# 3.1.10.2 Контракт watermark для регулярной загрузки регионов 66, 77, 78

## Цель
- Хранить подтвержденную границу успешной загрузки по каждому региону (`66`, `77`, `78`).
- Использовать watermark для построения следующего окна инкремента в регулярном процессе.

## Ключ watermark
- `(source_system, entity_name, region_code)`
- Для текущего контура:
  - `source_system='trudvsem'`
  - `entity_name='vacancies'`
  - `region_code in ('66','77','78')`

## Таблица (предложение)
- `mon.watermarks`
- Поля:
  - `source_system text not null`
  - `entity_name text not null`
  - `region_code text not null`
  - `watermark_value timestamptz not null`
  - `updated_at timestamptz not null default now()`
  - `updated_by_run_id text null`
  - `notes text null`
- PK: `(source_system, entity_name, region_code)`

## Аудит изменений watermark (append-only)
- `mon.watermark_history`
- Назначение:
  - хранить историю всех изменений watermark отдельным журналом (immutable log).
- Поля:
  - `id bigserial primary key`
  - `source_system text not null`
  - `entity_name text not null`
  - `region_code text not null`
  - `old_watermark_value timestamptz null`
  - `new_watermark_value timestamptz not null`
  - `changed_at timestamptz not null default now()`
  - `changed_by_run_id text null`
  - `change_source text not null` (например, `watermarks_trigger_insert` / `watermarks_trigger_update`)
  - `notes text null`
- Индексы:
  - `(source_system, entity_name, region_code, changed_at desc)`
  - `(changed_by_run_id)`

### Правила append-only
- История пишется автоматически trigger'ом на `mon.watermarks`:
  - `AFTER INSERT OR UPDATE` -> запись в `mon.watermark_history`.
- Для таблицы `mon.watermark_history` запрещены изменения существующих строк:
  - `BEFORE UPDATE` -> исключение,
  - `BEFORE DELETE` -> исключение.
- Таким образом журнал ведется только вставками (append-only).

## Построение окна
Для каждого региона отдельно:
1. Читаем текущий watermark.
2. `window_from = watermark_value`.
3. `window_to = now_utc - safety_lag` (например, 5–10 минут).
4. Если `window_to <= window_from`, регион в этом цикле пропускается.

## Правило обновления watermark
- Обновлять watermark только при `success` run данного региона.
- Новое значение — `window_to` текущего run (рекомендуемый режим).
- При `failed`/`partial` watermark не изменяется.
- Разрешено только монотонное движение вперед (`new_value > old_value`).

## Конкурентность и orchestration
- Регионы грузятся отдельными child run (`66`, затем `77`, затем `78`) последовательно.
- `master-dag` запускается с `max_active_runs=1`, чтобы исключить гонки за watermark.

## Backfill
- Ручной backfill не должен автоматически двигать watermark регулярного контура.
- После успешного backfill watermark меняется отдельным явным шагом (по решению оператора).

## Наблюдаемость
- Каждое изменение watermark должно иметь след в `updated_at`, `updated_by_run_id`.
- Каждое изменение watermark дублируется в `mon.watermark_history` как отдельное событие аудита.
- Детальные метрики исполнения и ошибки берутся из `mon.pipeline_runs`.
