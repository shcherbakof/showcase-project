# 2.1 Стандарт разработки (рабочий, Lite)

Версия: v2  
Статус: активный рабочий стандарт для этого репозитория (без CI)
Источник: рабочая агрегированная версия требований для текущего проекта

## 1) Scope

Документ обязателен для:

- `src/**` (prod-like Python код)
- `airflow/dags/**` (DAG и task-логика)
- `sql/**` (DDL/DML, миграции)
- ETL/операционных скриптов, которые участвуют в пайплайне

Документ не обязателен для:

- исследовательских ноутбуков (`*.ipynb`)
- ad-hoc SQL для разового анализа

Критичная логика:

- ingest/fetch/paging/retry
- запись в RAW/quarantine
- watermark/cursor и run status
- расчеты/трансформации, влияющие на KPI

## 2) Уровни требований

- `MUST` — обязательно
- `SHOULD` — желательно, отклонение требует краткого объяснения в PR/коммите
- `MAY` — опционально

## 3) Целевая структура кода

```text
src/
  trudvsem/
    fetch_layer.py
    raw_writer.py
    run_metrics.py
    contracts.py
    exceptions.py
    config.py
    logging_utils.py
  jobs/
    raw_ingest.py

test/
  test_fetch_layer.py
  test_raw_writer.py
  test_run_metrics.py

sql/db/project/migrations/
  *.sql
```

Принцип: I/O (HTTP/DB/FS) отдельно от бизнес-логики.

## 4) Python/ETL правила

### MUST

- Одна функция = одно действие.
- Публичные функции/классы: обязательны `type hints` и `docstring`.
- Не использовать `print` в прикладном коде; только `logging`.
- Таймауты обязательны для HTTP/DB вызовов.
- Retry только на временные ошибки (`429`, `5xx`, timeout/connection), с backoff + jitter.
- Исключения не “глотать”; ловить только ожидаемые.
- User-facing ошибки (CLI/UI): RU. Технические сообщения (log/exception): EN.
- Сообщения не должны раскрывать секреты/PII.
- В ошибках и логах использовать `run_id`/`error_code` там, где доступен контекст запуска.
- Идемпотентность загрузки обязательна.
- Конфигурация и секреты только через env/конфиг; не в коде и не в логах.
- Для CLI/ETL: поддерживать `--dry-run`, `--log-level`, параметры периода/окна запуска.
- Для batch-процессов: предсказуемые exit codes (`0` успех, `!=0` ошибка).
- Для долгих задач: graceful shutdown и cleanup ресурсов.

### SHOULD

- Длина функции до ~60 строк.
- Модуль до ~500 строк.
- Негативные тесты на критичных участках.
- `Any` только с комментарием причины.
- Подавления (`noqa`, `type: ignore`, skip test) только адресно и с причиной.

### MAY

- Кастомные доменные исключения.
- Pydantic для валидации конфигурации.

## 5) Data/Contract правила

### MUST

- Проверка минимального контракта RAW до записи:
  - `vacancy_id` (`id`)
  - `source_modified_at_raw` (`date_modify`)
  - `region_code_raw` (`region.region_code`)
- При нарушении контракта запись уходит в `raw.quarantine`.
- Для каждого нарушения контракта определено действие: `fail` / `warn` / `quarantine`.
- Временные метки в явной TZ (предпочтительно UTC), формат ISO 8601.
- Явная политика для null/дубликатов/таймзон в трансформациях.
- Статус run фиксировать в `mon.pipeline_runs` (`success|partial|failed`) по утвержденным правилам.
- Для incremental явно определять watermark/cursor и правила его обновления.

### SHOULD

- Fail-fast на критичных нарушениях контракта.
- Отдельные метрики на contract violations.
- Не использовать случайность без `seed` в детерминируемых расчетах.

## 6) SQL/DB правила

### MUST

- Для production SQL: запрет на `SELECT *`.
- Явные `JOIN` условия и явные списки колонок.
- Явные `CAST` для ключевых полей, где это важно для контракта.
- Параметризованные SQL-запросы в коде.
- Изменения схемы только через `sql/db/project/migrations/*.sql`.
- Для многошаговых изменений — транзакционность.
- Стратегия DDL/DML должна быть явной: где append-only, где upsert.
- Для схем: additive-first изменения до removal.

### SHOULD

- Единый SQL-стиль и читаемые CTE (один CTE = одна трансформация).
- Явно фиксировать SQL dialect, если используется более одного движка.

## 7) DBT правила (если используется)

### MUST

- Слойная модель: `staging` / `intermediate` / `marts`.
- `dbt parse` и `dbt test` для ключевых моделей/sources.
- Базовые тесты: `not_null`, `unique`, `relationships`, `accepted_values` (где применимо).
- Для incremental: явные `unique_key` и стратегия обновления.
- Бизнес-логику не прятать в Jinja-макросах.

### SHOULD

- `dbt source freshness`.
- `dbt docs` с описанием моделей и ключевых колонок.

## 8) Наблюдаемость и эксплуатация

### MUST

- Структурированное логирование (для ETL минимум единый формат полей).
- Корреляционный идентификатор: `run_id` (и/или `job_id`, `request_id`).
- Базовые метрики: длительность, количество обработанных строк, количество ошибок/отброшенных записей.

### SHOULD

- Явные пороги деградации (warning/error) для объема и freshness.

## 9) Безопасность данных

### MUST

- Secret scanning перед публикацией изменений (локально).
- Проверка зависимостей на уязвимости (локально).
- Маскирование PII в логах/ошибках и запрет утечки чувствительных данных в репозиторий.
- Валидация путей/файловых операций при user input (защита от path traversal).
- Ограничение размера входных данных для защиты от memory/DoS проблем.
- Least privilege для БД и сервисных аккаунтов.

### SHOULD

- Классификация полей ключевых таблиц на PII/non-PII.

## 10) Ноутбуки

### MUST

- Ноутбук не источник prod-логики.
- Переиспользуемая логика выносится в `.py`.
- Параметры входа/запуска фиксируются явно.

### SHOULD

- Очищать output перед коммитом.
- Использовать парный `.py` (например, через jupytext) для ревью.

## 11) Репозиторий и процессы (Lite без CI)

### MUST

- Единый локальный quality gate перед завершением задачи:

1. `.venv/bin/python -m unittest discover -s test -p 'test_*.py'`
2. `make init-db` (если затронуты миграции/схема)
3. `make smoke` (для e2e smoke)

- Документация по запуску и проверкам должна быть актуальна ([`scripts/README.md`](../../../scripts/README.md)).

### SHOULD

- Поддерживать pre-commit набор: formatter/linter/type checks/secret scan.
- Не смешивать рефакторинг и новую фичу в одном изменении.

## 12) Definition of Done

Задача считается завершенной, если:

1. Код соответствует `MUST` разделам этого документа.
2. Есть тесты на happy-path и минимум один негативный сценарий.
3. Обновлена документация/чеклист по факту выполненных шагов.
4. Для DB-изменений есть миграция и подтверждено применение через `make init-db`.
5. В логике запуска сохранены идемпотентность и наблюдаемость (`run_id`, метрики, статус).
6. Для incremental-задач зафиксированы watermark/cursor и правила update.

## 13) План усиления (когда появится CI)

- PR gates: format/lint/type/tests
- `ruff`, `mypy/pyright`, `pytest`, `sqlfluff`, `pre-commit`
- secret scan и dependency scan в CI
- для dbt: `dbt parse`, `dbt test`, `dbt source freshness`
