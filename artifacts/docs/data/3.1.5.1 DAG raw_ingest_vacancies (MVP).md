# 3.1.5.1 DAG raw_ingest_vacancies (MVP)

## Контекст использования в текущем проекте

- `raw_ingest_vacancies` — это **исполняющий (child) DAG** для фактической загрузки RAW-данных.
- В регулярном контуре он запускается master-оркестратором [`raw_master_regions`](3.1.10.3%20Master-DAG%20+%20Watermark:%20реализация%20и%20валидация.md), который:
  - рассчитывает окна по `mon.watermarks`,
  - передает `window_from/window_to/region_code` через `dag_run.conf`,
  - обновляет watermark только после `success` child-run.
- Практический режим эксплуатации:
  - для ежедневной регулярной загрузки основной вход — `raw_master_regions`;
  - `raw_ingest_vacancies` используется как сервисный DAG для ручных запусков (ad-hoc, отладка, точечный прогон окна/региона).

### Важно про пересечения запусков

- Если `raw_ingest_vacancies` запущен вручную на то же окно/регион, где уже идет прогон из master, пересечение по данным возможно.
- Дедупликация обеспечена на уровне БД:
  - `raw.vacancies` имеет уникальный ключ `(source_system, vacancy_id, source_modified_at_raw)`;
  - запись выполняется с `ON CONFLICT DO NOTHING`.
- Следствие:
  - дубли “версий” в `raw.vacancies` не размножаются;
  - в метриках второго прогона растет `raw_rows_skipped_conflict`;
  - в `mon.pipeline_runs` остаются отдельные записи по каждому `run_id`, что увеличивает операционный шум.

Документ фиксирует реализацию подпункта `1.5.1`: сбор DAG `raw_ingest_vacancies` со стадиями `compute_window -> fetch_pages -> extract_items -> write_raw -> write_run_stats`.

## Структура DAG

1. `compute_window`

- рассчитывает окно загрузки (`window_from/window_to`);
- поддерживает ручной override через `dag_run.conf` (`window_from`, `window_to`);
- формирует `run_id`, `run_type`, лимиты paging/safety.

2. `fetch_pages`

- вызывает `TrudvsemFetcher.iter_pages(...)`;
- использует retry/backoff/jitter/safety stop;
- сохраняет страницы в JSON-артефакт (`/tmp/raw_ingest_<run_id>_pages.json`);
- передает `fetch_diagnostics`.

3. `extract_items`

- читает страницы из артефакта;
- формирует батчи для записи;
- сохраняет батчи в JSON-артефакт (`/tmp/raw_ingest_<run_id>_batches.json`).

4. `write_raw`

- пишет батчи в `raw.vacancies` и `raw.quarantine` через `RawBatchWriter`;
- сохраняет результаты батчей в JSON-артефакт (`/tmp/raw_ingest_<run_id>_write_results.json`).

5. `write_run_stats`

- агрегирует fetch/write метрики через `RunMetricsAccumulator`;
- пишет итог в `mon.pipeline_runs` через `PipelineRunsWriter`;
- trigger rule: `all_done` (run stats пишутся даже при падении upstream).

## Особенности MVP

- Используются промежуточные JSON-файлы в `/tmp`, чтобы не перегружать XCom большими payload.
- При upstream failure задача `write_run_stats` все равно выполняется и фиксирует `failed/partial/success`.
- Подключение к БД берется из `PROJECT_DB_URI`.
