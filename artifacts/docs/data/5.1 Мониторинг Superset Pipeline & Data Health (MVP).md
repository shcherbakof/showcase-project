## 2) Согласованные статус-карточки (п.3 из 5.1)

В `mon.v_pipeline_health_status_cards` реализованы поля:

- `latest_run_status` (`success/partial/failed`)
- `quality_label` последнего run (`ok/warning/failed`)
- `freshness_delay_min`
- `raw_rows_today`, `stg_rows_today`, `mart_rows_today`
- `dq_warning_count`, `dq_error_count`

## 3) Выбранные источники (логически согласованные)

- `latest_run_status`/`quality_label`: из `mon.pipeline_runs` по последнему run DAG `stg_marts_pipeline` (через `mon.v_pipeline_health_freshness_current` и `mon.v_pipeline_health_last_runs`).
- `freshness_delay_min`: `now() - max(raw.vacancies.ingested_at)` в минутах.
- `raw_rows_today`: количество строк `raw.vacancies` за текущий день `Europe/Moscow`.
- `stg_rows_today`: количество строк `mart.vacancy_daily_snapshot` за текущий `dt`.
- `mart_rows_today`: количество строк `mart.market_daily_kpis` за текущий `dt`.
- DQ-метрики (`UNKNOWN`, `% без зарплаты`, future/null timestamp): из `mart.vacancy_daily_snapshot` + `mon.v_stg_vacancies_dq`.

Примечание: все daily-метрики считаются в `Europe/Moscow`.

## 4) Warning/Error пороги (строго по 5.1, без ручных исключений)

Реализованные пороги:

- Freshness:
  - warning: `freshness_delay_min > 360` (6ч)
  - error: `freshness_delay_min > 720` (12ч)
- Volume drop (day-over-day):
  - warning: падение `<= -40%`
  - error: падение `<= -70%`
- DQ `%UNKNOWN`:
  - warning: `> 20%`
  - error: `> 40%`

Дополнительно критическими DQ считаются:

- `critical_emptiness = true`
- `source_modified_at_future_rows > 0`

## 5) Структура Pipeline & Data Health (1 страница)

Подготовленные dataset-источники покрывают 5 секций:

1. Status cards (`mon.v_pipeline_health_status_cards`)
2. Freshness (`mon.v_pipeline_health_freshness_current`)
3. Volumes trend (`mon.v_pipeline_health_volumes_daily`)
4. DQ metrics (`mon.v_pipeline_health_dq_daily`, `mon.v_pipeline_health_dq_current`)
5. Last runs (`mon.v_pipeline_health_last_runs`)

## 6) Как проверить после деплоя

1. Применить миграции БД (`make init-db`).
2. Инициализировать Superset (`make up-superset`) — datasource manifest будет импортирован.
3. В Superset открыть БД `project_db` и убедиться, что datasets из `mon.v_pipeline_health_*` доступны.

## 7) Фактическая проверка в текущем окружении

Проверки выполнены после применения `010` и `011`:

1. `make init-db`:

- миграции `010_superset_pipeline_health_mvp.sql` и `011_superset_pipeline_health_fallbacks.sql` применены.

2. `mon.v_pipeline_health_status_cards`:

- `count(*) = 1`;
- текущий статус: `latest_run_status=failed`, `quality_label=failed`, `dq_error_count=2`.

3. `mon.v_pipeline_health_freshness_current`:

- `latest_run_id='n/a'`, `latest_run_status='failed'`, `freshness_severity='error'`.

4. `mon.v_pipeline_health_volumes_daily`:

- данные по последним дням читаются корректно (`raw/stg/mart` + DoD `%`).
