# 3.3.1 Ручные исследования перед реализацией MARTS

Документ фиксирует вопросы, которые нужно вручную согласовать до реализации блока `3` (MARTS), чтобы не зашить неверную бизнес-семантику в SQL.

## 1) Таймзона `dt` для MARTS

Вопрос для ручного решения:

- Какая таймзона считается канонической для дня `dt`: `UTC` или `Europe/Moscow`?

Развернутый комментарий:

- От этого напрямую зависят дневные срезы (`active/new/closed`) и совместимость с Excel-отчётом.
- Если выбрать `UTC`, на границах суток российские события будут попадать в «соседний день» с точки зрения бизнеса.
- Если выбрать `Europe/Moscow`, нужны явные конверсии timestamp -> local day в каждой витрине.

Моё мнение:

- Для текущего кейса логичнее фиксировать `dt` в `Europe/Moscow` как бизнес-день.

Мнение пользователя:

- Использовать `Europe/Moscow +3`

## 2) Определение метрик `active/new/closed`

Вопрос для ручного решения:

- Какие точные правила использовать для `active`, `new`, `closed` на день `dt`?

Развернутый комментарий:

- Без формального определения метрики будут «правильные технически», но спорные аналитически.
- Нужно заранее решить, что является источником истины для активности: `status_norm/is_active` в STG или событие изменения статуса между днями.
- Для `closed` особенно важно: это «все неактивные на конец дня» или «перешедшие в неактивные в этот день».

Моё мнение:

- Брать `active` по `is_active=true` на конец дня, `new` по первому появлению вакансии, `closed` как переход `active -> inactive` в рамках дня.

Мнение пользователя:

- Брать `active` по `is_active=true` на конец дня, `new` по первому появлению вакансии, `closed` как переход `active -> inactive` в рамках дня

## 3) Правило для "новой вакансии"

Вопрос для ручного решения:

- Что считать "new": первое появление в STG или событие по `source_modified_at`?

Развернутый комментарий:

- `first_seen_in_stg` устойчиво к переизданиям записи в источнике.
- Опора только на `source_modified_at` может дать ложные "new" при переоткрытии/редактировании старой вакансии.
- Для ретро-перезаливок и backfill это решение критично для стабильности KPI.

Моё мнение:

- Лучше считать `new` по `first_seen_in_stg` (минимальный `last_raw_ingested_at`/первый день присутствия `vacancy_id` в STG-snapshot).

Мнение пользователя:

- Считать "new": первое появление в STG

## 4) Набор зарплатных KPI

Вопрос для ручного решения:

- Какие зарплатные агрегаты обязательны в `mart_market_daily_kpis`?

Развернутый комментарий:

- Нужен фиксированный набор (например `median`, `p75`, `p90`, доля вакансий с зарплатой), иначе витрина будет постоянно меняться.
- Отдельно надо решить, считаем ли агрегаты только по записям с валидной зарплатой или пытаемся заполнять null-значения эвристикой.
- Важно сразу выбрать устойчивый метод расчёта квантилей в Postgres.

Моё мнение:

- Стартовый минимум: `salary_median`, `salary_p75`, `salary_p90`, `salary_coverage_pct`.
- Считать только по записям, где `salary_mid is not null`.

Мнение пользователя:

- Согласен. Берем стартовый миниум

## 5) Политика по категориям `UNKNOWN`

Вопрос для ручного решения:

- Включаем ли `UNKNOWN` в KPI и топы или исключаем?

Развернутый комментарий:

- Исключение `UNKNOWN` улучшает «красоту» витрин, но скрывает проблемы качества данных.
- Включение `UNKNOWN` даёт прозрачность, но может визуально «портить» топы на раннем этапе.
- Это решение должно быть единым для region/profession/status, чтобы не было смешанной логики.

Моё мнение:

- Включать `UNKNOWN` в расчёты как полноценную категорию, а в отчётах показывать отдельно.

Мнение пользователя:

- Согласен, включаем `UNKNOWN` в расчёты как полноценную категорию

## 6) Правила для `mart_employer_activity`

Вопрос для ручного решения:

- Как обращаться с `UNKNOWN_EMPLOYER:*` в employer-витрине и топах работодателей?

Развернутый комментарий:

- Если включать `UNKNOWN_EMPLOYER:*` в топы без ограничений, они могут доминировать и снижать ценность витрины.
- Если полностью исключить, можно потерять значимую долю рынка и занизить агрегаты.
- Нужен баланс: агрегаты «всего рынка» и отдельная логика для публичных top-N.

Моё мнение:

- В агрегатах включать всех, включая `UNKNOWN_EMPLOYER:*`.
- В публичных top employers — исключать `UNKNOWN_EMPLOYER:*` и показывать отдельный блок "Unknown employers".

Мнение пользователя:

- Поддерживаю твое мнение
