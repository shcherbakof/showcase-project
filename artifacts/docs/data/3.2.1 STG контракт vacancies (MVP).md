# 3.2.1 STG контракт vacancies (MVP)

Документ фиксирует утверждённый контракт для подпункта `2.1` из верхнеуровневого чек-листа.

## 1) `stg.vacancies`

Назначение: слой актуального состояния вакансий, где 1 строка = актуальная версия по `vacancy_id`.

Утверждённые поля контракта:

- `vacancy_id text primary key`
- `source_system text not null default 'trudvsem'`
- `run_id text not null` (run, который последним обновил строку STG)
- `source_modified_at timestamptz not null` (временная метка версии из источника)
- `region_raw text not null` (сырой регион из payload)
- `status_raw text not null` (сырой статус вакансии из payload)
- `salary_raw jsonb null` (сырой salary-объект без нормализации)
- `profession_raw text null` (сырое имя профессии/направления из payload)
- `employer_key text not null`
- `title text null`
- `last_raw_ingested_at timestamptz not null default now()`
- `stg_updated_at timestamptz not null default now()`

Примечание: legacy-колонки раннего baseline (`region`, `employer`, `published_at`, `loaded_at`) сохраняются для обратной совместимости и будут удалены отдельным cleanup-шагом после перевода загрузки на новый контракт.

## 2) Ключ работодателя (`employer_key`)

Принятое правило (детерминированный fallback-каскад):

1. `employer.inn` (если заполнен)
2. `employer.companycode` (если заполнен)
3. `employer.id` (если заполнен)
4. `UNKNOWN_EMPLOYER:<vacancy_id>` (если у вакансии нет стабильного идентификатора работодателя)

Цель: не терять запись в STG при неполных employer-атрибутах, но сохранить детерминизм upsert-ключа для работодателя.

## 3) Сырые поля, которые переносим в STG «как есть»

- `status_raw`
- `salary_raw`
- `region_raw`
- `profession_raw`

Нормализация (`is_active`, `salary_from/salary_to/...`, категории UNKNOWN) делается на шаге `2.2`.
