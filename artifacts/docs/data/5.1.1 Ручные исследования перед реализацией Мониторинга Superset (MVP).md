# 5.1.1 Ручные исследования перед реализацией Мониторинга Superset (MVP)

Документ фиксирует вопросы, которые нужно вручную согласовать до реализации блока `5` из [`artifacts/docs/data/3. Шаги выполнения checklist.md`](3.%20Шаги%20выполнения%20checklist.md), чтобы дашборд мониторинга был полезным для эксплуатации и не превращался в «витрину без действий».

## 1) Целевая аудитория дашборда

Вопрос для ручного решения:

- Кто основной пользователь страницы `Pipeline & Data Health`: инженер/аналитик/руководитель?

Развернутый комментарий:

- Без целевой аудитории сложно выбрать нужную детализацию: инженеру важны диагностика и drill-down, руководителю — несколько верхнеуровневых сигналов.
- Если смешать всё в один слой, дашборд становится перегруженным и теряет практическую ценность.

Моё мнение:

- MVP-версия должна быть в первую очередь для операционного контроля инженером, но с понятными агрегатами для быстрого статуса.

Мнение пользователя:

- Поддерживаю. Дашборд делаем для операционного контроля инженером с понятными агрегатами для быстрого статуса:
  - Какие агрегаты стоит взять?

## 2) Гранулярность и период обзора

Вопрос для ручного решения:

- Какой базовый период показываем по умолчанию: 7/14/30 дней?

Развернутый комментарий:

- Слишком короткий период плохо ловит тренды, слишком длинный размывает аномалии.
- Нужно сразу решить, от какого `dt` и в какой TZ строятся временные графики.

Моё мнение:

- По умолчанию 14 дней, с быстрым переключением на 7 и 30 дней.
- Все графики по `Europe/Moscow`.

Мнение пользователя:

- Поддерживаю
  - По умолчанию 14 дней, с быстрым переключением на 7 и 30 дней.
  - Все графики по `Europe/Moscow`.

## 3) Freshness-показатели

Вопрос для ручного решения:

- Какие freshness-метрики считаются «обязательными»: `max(ingested_at)`, `max(source_modified_at)`, `last_success_run`, latency до now?

Развернутый комментарий:

- Именно freshness обычно первым сигналит о «тихой поломке».
- Важно определить пороги warning/error, иначе метрики есть, но решений по ним нет.

Моё мнение:

- Обязательно показывать:
  - `last_success_run_time`,
  - `max_raw_ingested_at`,
  - `max_stg_source_modified_at`,
  - задержку в минутах до now.
- Порог warning/error — зафиксировать отдельно (см. пункт 8).

Мнение пользователя:

- Поддерживаю:
  - Обязательно показывать:
    - `last_success_run_time`,
    - `max_raw_ingested_at`,
    - `max_stg_source_modified_at`,
    - задержку в минутах до now.
  - Порог warning/error — зафиксировать отдельно (см. пункт 8).

## 4) Объёмы (volumes) по слоям

Вопрос для ручного решения:

- Какие именно объёмы считаем «каноническими» по дням: RAW/STG/MART по строкам, плюс изменения day-over-day?

Развернутый комментарий:

- Только абсолютные объёмы не всегда информативны; важны относительные отклонения.
- Нужно решить, считаем по `run_id` или по календарному `dt` после консолидации.

Моё мнение:

- Вынести 3 ряда: `raw_rows`, `stg_rows`, `mart_rows` по `dt`.
- Добавить `% diff to previous day` как вспомогательный индикатор.

Мнение пользователя:

- Поддерживаю:
  - Вынести 3 ряда: `raw_rows`, `stg_rows`, `mart_rows` по `dt`.
  - Добавить `% diff to previous day` как вспомогательный индикатор.

## 5) DQ-блок и приоритеты провалов

Вопрос для ручного решения:

- Какие DQ-проверки показываем как ключевые в MVP и что считать критичным?

Развернутый комментарий:

- DQ-секцию легко перегрузить; нужен короткий список high-signal метрик.
- Критичность должна совпадать с policy `warning-gate` из блока 4.

Моё мнение:

- В MVP вывести:
  - `% UNKNOWN` по region/profession,
  - `% вакансий без зарплаты`,
  - `source_modified_at_future_rows`,
  - critical emptiness (`snapshot/market/employer` rows = 0).

Мнение пользователя:

- Поддерживаю:
  - `% UNKNOWN` по region/profession,
  - `% вакансий без зарплаты`,
  - `source_modified_at_future_rows`,
  - critical emptiness (`snapshot/market/employer` rows = 0).

## 6) Аномалии объёмов/пустот

Вопрос для ручного решения:

- Какой метод детекта аномалий используем в MVP: простые пороги, rolling baseline, z-score?

Развернутый комментарий:

- Сложные методы без истории дают шум.
- Для MVP лучше простая и прозрачная логика, которую легко объяснить при инциденте.

Моё мнение:

- Использовать простые пороги:
  - падение объёма > X% к вчера,
  - «пустой день» при непустом предыдущем периоде,
  - freshness задержка > Y минут.

Мнение пользователя:

- Поддерживаю:
  - Используем простые пороги:
    - падение объёма > X% к вчера,
    - «пустой день» при непустом предыдущем периоде,
    - freshness задержка > Y минут.

## 7) Связь с quality-marker и `mon.pipeline_runs`

Вопрос для ручного решения:

- Как дашборд должен отражать `quality_label` (`success/partial/failed`) и `error_summary` из run-логов?

Развернутый комментарий:

- Именно связь дашборда с фактическим статусом run делает мониторинг операционным, а не только «аналитическим».
- Нужен быстрый переход от красного индикатора к конкретному run_id и ошибке.

Моё мнение:

- Отдельная таблица последних запусков (`run_id`, `status`, `quality_label`, `error_summary`, `duration_sec`) обязательна.

Мнение пользователя:

- Поддерживаю
  - Отдельная таблица последних запусков (`run_id`, `status`, `quality_label`, `error_summary`, `duration_sec`) обязательна.

## 8) Пороги warning/error (операционный контракт)

Вопрос для ручного решения:

- Какие конкретные пороги warning/error принимаем для freshness, volumes и DQ?

Развернутый комментарий:

- Без численных порогов нельзя однозначно интерпретировать «жёлтый» и «красный» статус.
- Пороги должны быть реалистичны под текущий двухслотовый режим (07:00, 16:00 MSK).

Моё мнение:

- Стартовые MVP-пороги (предложение):
  - Freshness warning: > 6 часов, error: > 12 часов.
  - Volume drop warning: > 40% day-over-day, error: > 70%.
  - DQ warning: `%UNKNOWN` > 20%, error: > 40%.

Мнение пользователя:

- Поддерживаю:
  - Берем стартовые пороки MPV
    - Freshness warning: > 6 часов, error: > 12 часов.
    - Volume drop warning: > 40% day-over-day, error: > 70%.
    - DQ warning: `%UNKNOWN` > 20%, error: > 40%.

## 9) Минимальная структура страницы Superset (1 страница)

Вопрос для ручного решения:

- Подтверждаем ли структуру одного листа: Health header -> Freshness -> Volumes -> DQ -> Last runs?

Развернутый комментарий:

- Единая структура нужна для предсказуемого daily-review.
- Если блоки расположены хаотично, пользователи пропускают критичные сигналы.

Моё мнение:

- Для MVP сделать 5 секций на одной странице:
  1. Status cards,
  2. Freshness,
  3. Volumes trend,
  4. DQ metrics,
  5. Last pipeline runs.

Мнение пользователя:

- Поддерживаю:
  1. Status cards,
  2. Freshness,
  3. Volumes trend,
  4. DQ metrics,
  5. Last pipeline runs.
