## Собрать из документации API

Документация к API расположена по адресу: <https://trudvsem.ru/opendata/api>

- Работа с API осуществляется по протоколу HTTP
- Все вызовы API реализуются HTTP-методом GET
- Ответ на запрос в API формируется только в формате JSON.
- Даты форматируются в соответствии с ISO 8601.
- Количество записей, включаемых в ответ на запрос, не превышает 10 000 шт.
- Версионность API. Номер версии указывайте целым числом в формате
  - <http://opendata.trudvsem.ru/api/v1/vacancies>
- Схема предоставляемых по API данных
  - <http://opendata.trudvsem.ru/api/v1/vacancies/application.wadl>

### Обязательные и опциональные параметры (окно изменений, регион, paging, page_size)

- Окно измнений
  - Система хранит дату последней модификации записи. В API поддерживается метод, который возвращает все изменённые записи, начиная с заданной даты. Вариант — записи, которые изменили в указанный диапазон времени. Для этого в запросе после знака «?» следует указывать даты и время. Пример. Дата указывается в формате ISO 8601:
  - <http://opendata.trudvsem.ru/api/v1/vacancies?offset=1&limit=100&modifiedFrom=2016-07-10T15:00:00Z>
  - <http://opendata.trudvsem.ru/api/v1/vacancies?modifiedFrom=2016-07-10T15:00:00Z&modifiedTo=2016-10-10T15:00:00Z>
- Регион
  - Информация о вакансиях в конкретном регионе:
    - <http://opendata.trudvsem.ru/api/v1/vacancies/region/%region_code%>
  - Коды региона
    - ?
- paging, page_size
  - Данные передаются постранично, не более 100 записей на странице. Для получения постраничного ответа необходимо уточнить два параметра в запросе:
  - число элементов (limit);
  - смещение (offset).
  - Они указываются после знака «?» в запросе:
    - <http://opendata.trudvsem.ru/api/v1/vacancies?offset=1&limit=100>

### модель paging (как понять, что страниц больше нет)

В документации нет явного правила завершения paging, поэтому модель определена по фактическому поведению API.

- Техническая схема запросов:
  - endpoint: `<http://opendata.trudvsem.ru/api/v1/vacancies/region/%region_code%>`
  - paging: `offset` + `limit` (используем `limit=100`, `offset=1,2,3...`)
- Проверка выполнялась в блокноте [3.1.1.1 stand.ipynb](3.1.1.1%20stand.ipynb).

**Наблюдение по API**
- Счетчик/граница страниц работает нестабильно: API может возвращать `meta.total`, но на глубокой странице вместо ожидаемого «пустого 200» отдаёт `500`.
- Пример для окна `2025-01-01T00:00:00Z` по регионам `66/77/78`: после серии успешных страниц API стабильно падает `500` на `offset=100`.

**Принятая рабочая модель paging**
- Идем последовательно `offset=1,2,3...`.
- Для `500` делаем до `5` retry.
- Если после 5 retry на очередной странице всё еще `500`, но до этого были успешно загружены страницы с данными:
  - считаем это фактической границей окна,
  - завершаем fetch корректно (без фатального падения).
- Если `500` возникает до первой успешной страницы с данными:
  - считаем запуск неуспешным.
- `meta.total` используем как диагностический сигнал, но не как критерий остановки.

Проверены и используются коды регионов:
- Москва: `77`
- Санкт-Петербург: `78`
- Свердловская область: `66`

### лимиты/429 (есть ли rate limit, рекомендации по backoff)

- По 429 ошибке на [странице](https://trudvsem.ru/opendata/api) про API нет никакой дополнительной информации. Поиск дополнительного контекста чз поисковые машины не дал результатов
  - Пока просто будем фиксировать ошибку. Возможно поймаем и там будет retry-after или что-то подобное
- Так как информации по 429 нет, -- сделаем backoff: экспоненциальна растущая паузу + случайное число, для того чтобы не синхронизироваться с другими клиентами
  - на 429 и 5xx/сетевые делать ретраи с backoff, на 4xx (кроме 429) обычно не ретраить
- Ограничить параллельность (часто 1–4 одновременных)
