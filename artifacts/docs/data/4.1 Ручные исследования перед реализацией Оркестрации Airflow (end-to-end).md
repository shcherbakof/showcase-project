# 4.1 Ручные исследования перед реализацией Оркестрации Airflow (end-to-end)

Документ фиксирует вопросы, которые нужно вручную согласовать до реализации блока `4` из [`artifacts/docs/data/3. Шаги выполнения checklist.md`](3.%20Шаги%20выполнения%20checklist.md), чтобы оркестрация была эксплуатационно стабильной и предсказуемой.

## 1) Архитектура оркестрации DAG

Вопрос для ручного решения:

- Какую схему принимаем: единый master DAG (`RAW -> STG -> MARTS -> DQ -> report`) или несколько DAG с явными trigger dependencies?

Развернутый комментарий:

- Единый DAG проще для мониторинга одного `run_id`, но сложнее по времени выполнения и перезапускам отдельных частей.
- Набор DAG-ов даёт более гибкий rerun и изоляцию ошибок, но увеличивает сложность связей и управления статусами.

Моё мнение:

- Для текущего MVP лучше 2 уровня: `raw_master_regions` отдельно, и downstream `stg_marts_pipeline` как второй DAG, связанный через trigger + conf.

Мнение пользователя:

- Поддерживаю. Берем `raw_master_regions` отдельно, и downstream `stg_marts_pipeline` как второй DAG, связанный через trigger + conf

## 2) Границы ответственности по слоям

Вопрос для ручного решения:

- Где проходит граница между RAW-контуром и STG/MART-контуром в оркестрации?

Развернутый комментарий:

- Если граница размыта, сложно понять, кто «виноват» при partial/fail и как правильно делать rerun.
- Явные boundaries упрощают recovery-процедуры и запись метрик в `mon.pipeline_runs`.

Моё мнение:

- Закрепить правило: RAW завершается после успешного ingestion+watermark, далее отдельный downstream DAG строит STG/MART/DQ/Excel.

Мнение пользователя:

- Поддерживаю

Вопрос для ручного решения:

- Какое ежедневное расписание и к какому времени (MSK) отчёт должен быть готов?

Развернутый комментарий:

Моё мнение:

## 4) Политика `partial` vs `failed`

Вопрос для ручного решения:

- Какие условия считаются `partial`, а какие строго `failed` для end-to-end DAG?

Развернутый комментарий:

- Это критично для единообразия `mon.pipeline_runs` и для алертов.
- Без формального контракта одни и те же инциденты будут по-разному интерпретироваться.

Моё мнение:

- `failed`: нет валидного результата слоя (например, STG/MART не построены).
- `partial`: слой построен, но есть DQ-нарушения/неблокирующие ошибки и данные пригодны с предупреждением.

Мнение пользователя:

- Поддерживаю твое мнение. Берем:
  - `failed`: нет валидного результата слоя (например, STG/MART не построены).
  - `partial`: слой построен, но есть DQ-нарушения/неблокирующие ошибки и данные пригодны с предупреждением.

## 5) Правила остановки по DQ

Вопрос для ручного решения:

- DQ-провалы блокируют downstream (Excel/публикацию) или допускается выпуск с warning?

Развернутый комментарий:

- Строгий stop защищает качество, но может создавать пропуски отчётов.
- Мягкий режим повышает доступность отчётов, но нужен явный флаг качества.

Моё мнение:

- Для MVP использовать policy "warning-gate": критичные DQ блокируют, некритичные помечают run как `partial` и разрешают выпуск.

Мнение пользователя:

- Поддерживаю. Используем policy "warning-gate": критичные DQ блокируют, некритичные помечают run как `partial` и разрешают выпуск.

## 6) Ретраи, таймауты, idempotency rerun

Вопрос для ручного решения:

- Какие retry/timeout параметры принимаем и какие этапы можно безопасно перезапускать?

Развернутый комментарий:

- Без этого возможны “бесконечные” ретраи или ручные перезапуски, которые портят SLA.
- Нужно зафиксировать, что rerun по одному `dt` должен быть детерминированным и не дублировать данные.

Моё мнение:

- Ограниченные retries + явные execution timeout; rerun по `dt` допускается для STG/MART при идемпотентной refresh-функции.

Мнение пользователя:

- Поддерживаю. Ограниченные retries + явные execution timeout; rerun по `dt` допускается для STG/MART при идемпотентной refresh-функции.

## 7) Backfill-режим

Вопрос для ручного решения:

- Как запускаем backfill диапазона дат: отдельный DAG/режим, какой параллелизм допустим?

Развернутый комментарий:

- Backfill без лимитов может конфликтовать с ежедневным расписанием и создавать конкуренцию за ресурсы.
- Нужны правила приоритета regular runs vs backfill runs.

Моё мнение:

- Отдельный backfill-режим с ограниченным параллелизмом и запуском вне основного SLA-окна.

Мне пользователя:

- Отдельный backfill-режим с ограниченным параллелизмом и запуском вне основного SLA-окна выполненный:
  - В виде блокнота ipynb для ручного запуска и дополнительных исследований
  - В виде дага, запускаемого вручную, и с параметрами
