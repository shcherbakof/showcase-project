## Требования к инфраструктуре (что считаем «готово»)

### 1.1 Цели

- Воспроизводимый локальный стенд «под ключ»: ревьюер поднимает всё только Docker’ом, без локального Python.
- Модульный запуск: поднимаем и отлаживаем по одному модулю (начинаем с Postgres), дальше Airflow, дальше Superset.
- Демо «из коробки»: Superset показывает 2 витрины без похода в API (минимальные seed-данные).
- Опциональная локальная отладка ETL из venv (VS Code), но основной прогон — внутри Airflow.

### 1.2 Границы (Scope)

Входит:

- Docker Compose стек с profiles: `db`, `db-init`, `airflow`, `superset`.
- Один контейнер Postgres и внутри 3 БД: `project_db`, `airflow_db`, `superset_db`.
- Инициализация/миграции/seed строго по порядку, повторяемо (как в проде).
- Хранилище raw: `jsonb` + audit-поля (payload, fetched_at, source, run_id).
- Таймзона стек/расписания: Europe/Moscow (+3).

Не входит (пока):

- Celery/Redis/Kubernetes/«как в мегакорпорации».
- Реальный prod-hardening (TLS, Vault, SSO, отдельные хосты).

### 1.3 Нефункциональные требования

- Кросс-ОС: macOS/Linux/Windows (только Docker Desktop/Compose v2).
- Версии фиксируются (image tags + lock зависимостей Python).
- Секреты не коммитим: `.env` в git нельзя, только `.env.example`.
- По умолчанию наружу публикуем Postgres: удобно для ревьюера.
- Ресурсы Docker Desktop:
  - minimum: 6 GB RAM / 2 CPU
  - recommended: 8 GB RAM / 4 CPU

### 1.4 Требования к инициализации (важно)

[НЕ ДЕЛАЙ ТАК, БЛЯДЬ]: полагаться на `docker-entrypoint-initdb.d` как на основной механизм — он одноразовый и ломает повторяемость.

Нужно:

- Отдельный сервис `db-init` (one-shot) с жёстким порядком применения:
  - роли/пользователи
  - БД
  - расширения
  - схемы
  - таблицы
  - seed

- Идемпотентность: повторный запуск `db-init` не должен ломать БД (и должен быть ожидаемо «no-op» или «применил только новое»).
- 2 reset-сценария:
  - hard reset: с удалением volume (дроп данных)
  - soft reset: пересоздать схемы/таблицы/seed без удаления datadir

### 1.5 Airflow / Superset (ключевые решения)

- Airflow executor: LocalExecutor (для MVP и отладки это ровно то, что нужно; Celery = зоопарк без пользы на старте).
- Метаданные Airflow/Superset: в том же Postgres, но в отдельных БД.
- Superset assets: храним в репо раздельно по сущностям; подключение к БД настраиваем через env/bootstrapping (без секретов в asset-файлах).
- Демо-дашборды: 2 штуки
  - бизнес-витрина (mart)
  - витрина состояния пайплайна (mon + dq)

### 1.6 Seed: SQL vs «python-seed контейнер»

- SQL seed: детерминированно, быстро, без сети, идеально для «дашборд из коробки».
- Python-seed контейнер: гибче (можно стянуть из API), но медленнее, флейки из-за сети/лимитов/изменений API.

Выбор для MVP: SQL seed (иначе «из коробки» превращается в «ну запусти сначала API-загрузку»).

Вопрос (наводящий): seed делаем минимальный (10–50 строк на ключевые таблицы mart/mon) или чуть богаче (чтобы графики выглядели как графики)?

### 3.5 Конфигурация через env

- Единственный источник конфигурации окружения: `.env`
- `.env.example` содержит:
  - порты
  - креды admin (локальные)
  - креды Postgres (пример)
  - параметры таймзоны

### 3.6 Runbook: как поднимать по модулям

- Модуль DB:
  - старт Postgres
  - ожидание healthcheck
  - запуск `db-init`
  - проверка smoke (наличие БД/схем/таблиц)

- Модуль Airflow:
  - старт airflow init (мета-БД, admin)
  - старт scheduler/webserver

- Модуль Superset:
  - init (миграции, admin)
  - создать подключение к `project_db`
  - импортировать assets из репо

### 3.7 Правила разработки init’ов (prod-style)

- Файлы строго с префиксом порядка: `000_`, `010_`, `020_`…
- Каждый скрипт:
  - либо идемпотентный (IF NOT EXISTS / upsert в таблицу миграций)
  - либо защищён транзакцией и проверками

- Любая ошибка = стоп выполнения (никаких “проглотил и поехал дальше”)

### 3.8 Локальная отладка (опционально venv)

- Поддерживаем два режима:
  - основной: Airflow запускает код в контейнере (истина для ревьюера)
  - опциональный: разработчик запускает части кода из `.venv`, используя host-port Postgres

- Требование: одинаковый набор зависимостей (lock один, расхождений быть не должно)

Твой выбор “DAG-и запускают код из `src`” — правильный. Единственное: DAG-и держи максимально тонкими, иначе ты сама себе устроишь мини-монолит в `dags/` (и будешь страдать).

### 3.9 Демо без API

- Seed делаем SQL (минимальный набор данных)
- Superset после инициализации должен показать оба дашборда сразу

### 3.10 Контроль качества инфраструктуры (минимум)

- healthchecks на сервисы
- smoke-команды/проверки в README
- понятные reset-сценарии
- “чистая” остановка (down без потери данных, если не hard reset)

### 4.2 Compose profiles (поведение)

- profile `db`
  - поднимает только Postgres (persist volume, порт наружу)

- profile `db-init`
  - запускает `db-init` one-shot, который:
    - ждёт healthcheck Postgres
    - применяет SQL в заданном порядке
    - завершает контейнер с кодом 0

### 4.3 Env-матрица (Postgres модуль)

Обязательные (MUST):

- `POSTGRES_IMAGE_TAG` (например, `16.x`)
- `POSTGRES_HOST_PORT` (по умолчанию `5432`, переопределяемо)
- `POSTGRES_SUPERUSER` (например, `postgres`)
- `POSTGRES_SUPERPASS`
- `PROJECT_DB=project_db`
- `PROJECT_USER=project_user`
- `PROJECT_PASS`
- `AIRFLOW_DB=airflow_db`
- `AIRFLOW_USER=airflow_user`
- `AIRFLOW_PASS`
- `SUPERSET_DB=superset_db`
- `SUPERSET_USER=superset_user`
- `SUPERSET_PASS`

Рекомендуемые (SHOULD):

- `POSTGRES_LOCALE` / `POSTGRES_ENCODING` (если хочешь предсказуемую сортировку/кодировку)
- `TZ=Europe/Moscow`

Про DSN (чтобы не путаться с localhost vs service-name):

- `PROJECT_DB_DSN_DOCKER` (host = имя сервиса Postgres в compose)
- `PROJECT_DB_DSN_HOST` (host = `localhost`, порт = `POSTGRES_HOST_PORT`)
  Аналогично при необходимости для airflow/superset DB.

### 4.4 Правила именования volume/сетей

Требование: имена не должны зависеть от “случайного имени папки у ревьюера”.

Рекомендую (MUST):

- `COMPOSE_PROJECT_NAME` задаём явно (в `.env`), это префикс всего.
- Network:
  - имя: `<project>_net`
  - driver: bridge

- Volumes:
  - postgres data: `<project>_pgdata`
  - (если будет) backups/artifacts: `<project>_pgbackups` и т.д.

Политика хранения данных:

- По умолчанию: named volume (кросс-ОС стабильнее).
- Опционально: bind mount для дебага (но это отдельный режим, не дефолт).

### 4.5 Reset-сценарии (контракт)

- Hard reset (DROP DATA):
  - down + удаление volumes Postgres

- Soft reset (KEEP DATA DIR):
  - SQL/скрипт, который:
    - очищает или пересоздаёт схемы `raw/stg/mart/mon` в `project_db`
    - сбрасывает seed и (если нужно) таблицы мониторинга
    - не трогает роли и сами БД
