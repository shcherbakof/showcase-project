Логика прогонов (операционка, как в проде, но локально)

- DAG1 ingest_vacancies_modified
  - окно: watermark (last_success_run) → now-Δ
  - retry/backoff, paging
  - append-only в raw_vacancies
  - upsert в stg_vacancies
  - запись метрик в pipeline_runs

- DAG2 ingest_employers_enrichment
  - достаёт employer keys из stg_vacancies
  - тянет работодателей, raw → stg upsert

- DAG3 build_marts_sql
  - SQL витрины mart\_\*

- DAG4 dq_and_finalize
  - DQ по raw/stg/mart → dq_results
  - финальный статус run
  - watermark двигается только при success

Компоненты, которые я бы заложила в docker-compose (минимально, без “зоопарка”)

Чек-лист “чтобы не было [ХУЙНЯ В ПРОДЕ]”

- Один Postgres, но чётко разделить схемы raw/stg/mart/mon (SoT слоёв понятен с первого взгляда)
- Airflow metadata DB: либо отдельная БД в том же Postgres, либо отдельный сервис postgres-airflow (в портфолио норм и так, и так)
- Идемпотентность: staging только через upsert по ключу vacancy_id / employer_key
- Watermark хранить в mon (например, в pipeline_runs или отдельной таблице) и обновлять только при success
- Артефакты Excel писать в отдельный volume и не путать с логами Airflow

1. Базовый стек и что за что отвечает

1.1 Docker + Docker Compose

- Определение: Docker — “контейнеры”, изолированные сервисы (Postgres, Airflow, Superset) с фиксированными версиями. Compose — файл, который поднимает всё одной командой.
- Зачем: чтобы у запускающего не плясали версии и зависимости.
- Нюансы:
  - Версии фиксируй (image tags), иначе “вчера работало, сегодня сломалось”.
  - Данные БД должны жить в volume/папке, иначе при пересоздании контейнера всё улетит.

  1.2 Python venv (твой код)

- Определение: venv — изолированная папка с питон-библиотеками только для проекта.
- Зачем: твой ETL/скрипты/тесты отдельно от системного Python.
- Нюансы:
  - `venv/` в git нельзя (только `requirements.txt` / `pyproject.toml`).
  - VS Code должен “видеть” интерпретатор из [`./.venv`](../../../.venv).

  1.3 Postgres

- Определение: реляционная БД. Тут будут raw/stg/mart + мониторинг.
- Зачем: единая “истина” по данным и витринам.
- Нюансы:
  - Схемы (namespaces) в БД: `raw`, `stg`, `mart`, `mon`.
  - Миграции/инициализация: при первом старте нужно создать схемы/таблицы (SQL в репо).
  - Доступы: пароль/юзер через `.env`, а не хардкод в коде.

  1.4 Airflow

- Определение: оркестратор задач. Он по расписанию запускает пайплайн, следит за ретраями, логами и статусами.
- Зачем: вместо “я руками запускаю скрипт” → “всё само, прозрачно”.
- Нюансы:
  - Airflow сам хранит свою мета-БД (статусы, расписания). Можно хранить в отдельной БД в том же Postgres или в отдельном контейнере Postgres.
  - Требуется “init” (создание таблиц метаданных, админ-пользователь).
  - DAG-и должны лежать в [`airflow/dags/`](../../../airflow/dags) и монтироваться как volume.

  1.5 Superset

- Определение: BI-вебка для дашбордов.
- Зачем: мониторинг пайплайна/витрин и “витрина для портфолио”.
- Нюансы:
  - Тоже имеет внутреннюю мета-БД (обычно SQLite в контейнере или отдельная БД). Для портфолио допустимо проще.
  - Нужно подключение к Postgres (как datasource).
  - Инициализация (создание админа, миграции).

  1.6 Твой ETL/ELT код

- Определение: Python-пакет/модуль, который:
  - тянет JSON по API
  - складывает raw (jsonb)
  - делает upsert в stg
  - строит mart
  - пишет monitoring-таблицы и (опционально) Excel-артефакты

- Нюансы:
  - Код должен быть идемпотентным (повторный запуск не ломает данные).
  - Конфиг через env (строки подключения, регионы, лимиты, окна).

3. Пошагово: установка и настройка компонентов

Шаг 0. Версии и требования

- Зафиксируй:
  - Python (например, 3.11)
  - Docker Desktop (актуальный)

- Почему: иначе “у него не работает” из-за несовпадений.

Шаг 1. Инициализация репозитория и базовых файлов

- Создай структуру папок (выше).
- Добавь:
  - `.gitignore`
  - `.env.example`
  - `README.md`

Нюансы:

- В `.env.example` только шаблоны:
  - `POSTGRES_USER=...`
  - `POSTGRES_PASSWORD=...`
  - `POSTGRES_DB=...`
  - `AIRFLOW__CORE__FERNET_KEY=...` (если используешь)
  - `AIRFLOW_UID=...` (часто нужно на Linux)

- Реальный `.env` — локально, не в git.

Шаг 2. Python venv для проекта (VS Code)

- Создай `.venv` в корне проекта.
- Выбери интерпретатор в VS Code: `./.venv/bin/python`.
- Поставь зависимости проекта (requests, pandas, sqlalchemy/psycopg, pydantic, etc.)

Нюансы:

- В репо хранится только:
  - `requirements.txt` (проще) или `pyproject.toml` (чище)

- Любые “локальные пути” в настройках VS Code (типа [`.vscode/settings.json`](../../../.vscode/settings.json)) можно коммитить, если они универсальные и не содержат машинных абсолютных путей.

Шаг 3. Postgres в Docker Compose

- Добавь сервис `postgres`.
- Примонтируй volume/папку для данных (например `./pgdata:/var/lib/postgresql/data`).

Нюансы:

- `pgdata/` в git нельзя.
- Порт наружу (обычно 5432) — ок, но если у человека порт занят, пусть меняет в `.env`.
- Инициализация схем/таблиц:
  - вариант A: `sql/init/*.sql` прокидывается в `/docker-entrypoint-initdb.d/` (выполнится при первом создании volume)
  - вариант B: отдельная команда/скрипт `make db-init` (предпочтительнее для повторяемости)
  - важно: init-скрипты в entrypoint выполняются только при “пустой” БД.

Шаг 4. Airflow в Docker Compose

- Добавь `airflow-webserver` и `airflow-scheduler`.
- DAG-и монтируй из [`./airflow/dags`](../../../airflow/dags).
- Логи монтируй в `./airflow/logs`.

Нюансы установки:

- Первый запуск требует:
  - миграции мета-БД Airflow
  - создание admin user

- Это обычно делается отдельным “init” сервисом в compose (одноразовый контейнер) или командой `airflow db migrate` + `airflow users create`.

Нюансы настройки:

- Executor: для портфолио обычно достаточно “простого” (не Celery).
- Конфиг Airflow через env переменные (не через правку файлов в контейнере).

Шаг 5. Superset в Docker Compose

- Добавь сервис `superset`.
- Настрой подключение к Postgres как datasource.

Нюансы установки:

- Требуется init:
  - миграции
  - создание admin

- Для воспроизводимости лучше держать:
  - инструкции в README
  - (опционально) seed-файлы с датасетами/дашбордами (это можно отложить)

Шаг 6. Сетевые имена и подключения

- Внутри compose все сервисы общаются по hostname = имени сервиса.
  - Пример: `postgres:5432`, а не `localhost:5432` (это типичная ловушка).

- Твой Python-код:
  - если запускается на хосте (в venv), то ему нужен `localhost:5432`
  - если запускается внутри контейнера Airflow, то `postgres:5432`

Нюансы:

- Это главная причина “у меня не коннектится”. Решение: две строки подключения (host и docker) или один DSN через env, а запуск строго из Airflow контейнера.

Шаг 7. “Кто-то будет запускать после” — сценарий запуска
Минимальный сценарий в README:

1. `cp .env.example .env` и заполнить
2. `docker compose up -d postgres`
3. выполнить db-init (если не через entrypoint)
4. `docker compose up -d airflow superset`
5. зайти в Airflow UI → включить DAG-и
6. проверить, что в Superset видны таблицы `mart_*`

Нюансы:

- Добавь “smoke checks”:
  - healthcheck у postgres
  - простой SQL “select 1”
  - проверка наличия схем/таблиц
